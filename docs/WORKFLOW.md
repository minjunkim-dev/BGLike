# 작업과 협업 규칙

GitHub 품질 운영은 1인 개발 기준입니다. 필수 승인 인원은 0명입니다. 위험별 최종 head 승인과 서버 설정은 [설정 기준선](REPOSITORY_SETUP.md)을 따릅니다. 기존 제품 협업과 권리 기록은 유지합니다.

## 작업과 결정

- GitHub Issue 하나에 목표, 완료 조건, 담당자 한 명을 적습니다. 기획 중인 항목은 구현 범위를 확정하기 전까지 개발 브랜치를 만들지 않습니다.
- 채팅이나 통화에서 내린 결정은 해당 Issue에 짧게 기록합니다. 막히면 작업 내용을 늘리기 전에 Issue에서 범위를 조정합니다.
- 기능 작업은 한 사람이 소유합니다. 필요하면 다른 사람에게 PR 검토를 요청합니다. 같은 `.tscn` 장면이나 LFS 바이너리를 동시에 수정해야 한다면 먼저 파일 담당을 나눕니다.

### 작업 선택과 종료

착수할 때, 새 결정이 도착했을 때, 작업을 마치기 전에 맡은 범위의 Issue·결정 코멘트·막는 관계를 확인합니다. 기존 지도나 Issue 진행 코멘트에 아래 상태와 다음 행동을 기록합니다. 결정 원문은 관련 티켓에 두고 연결합니다.

| 상태 | 다음 행동 |
| --- | --- |
| 실행 가능 | 확정된 범위와 개발 결정을 구현·검증하고 위험별 병합 조건까지 진행합니다 |
| 기획 답 대기 | 필요한 질문과 막히는 범위를 연결하고, 독립적인 실행 가능 항목을 계속합니다 |
| 사람 확인 대기 | 빌드·재현 방법·체크리스트를 준비하고 직접 확인하지 않은 항목을 적습니다 |
| 승인 대기 | 승인 대상의 정확한 SHA·산출물·영향·실행 명령을 준비하고 해당 단계 직전에 멈춥니다 |
| 완료 | Issue 완료 조건과 필요한 검증·리뷰·병합 결과를 연결합니다 |

한 Issue에 확정된 부분과 미확정 부분이 섞이면, 독립적으로 구현할 수 있는 확정 범위를 별도 Issue로 분리합니다. 막는 관계는 실제로 그 결정이 필요한 범위에만 연결합니다. 새 기획 답이 없다는 사실만으로 다른 항목을 대기시키지 않습니다.

종료 전에 맡은 범위의 승인된 실행 가능 항목이 남았는지 확인하고, 남았으면 계속 진행합니다. 도구·권한·CI 등 외부 조건 때문에 진행할 수 없으면 기획 대기와 구분해 대상·실패 근거·재개 조건을 기록합니다. 사용자가 명시한 기획 결정권과 승인 경계는 유지합니다.

### Issue 운영

문서는 **무엇이 정답인가**(규칙, 수치)를, Issue는 **지금 무엇을 하는가**(목표, 진행, 결정 기록)를 담습니다. 질문은 항상 **Issue 코멘트**에 적습니다. 기획이 문서를 쓰면서 아직 정하지 않은 항목은 문서에 ❓로 표시만 하고, 답이 나오면 문서를 고칩니다.

| 언제 | 무엇을 | 누가 |
|---|---|---|
| 기획이 범위를 넘길 때 | 기획 문서와 개발 요청서를 `docs/`에 PR로 올리고, 개발 Issue 하나를 엽니다. 본문에 문서 링크, 결정, 완료 조건을 적습니다 | 기획 |
| 개발 시작 | 작업 순서를 체크박스로 첫 코멘트에 적습니다 (개발이 직접 연 Issue면 본문에). 각 PR 본문에 `Refs #번호`를 적습니다 | 개발 |
| 회의나 채팅에서 결정 | 그 Issue에 코멘트 한 줄을 남깁니다. 문서를 바꿔야 하면 문서 PR 링크를 함께 적습니다 | 결정한 사람 |
| 범위가 달라질 때 | 본문을 고치지 않고 코멘트에 "변경 전 → 후" 표를 적습니다. 크게 바뀌면 새 Issue를 열고, 옛 Issue는 새 Issue 링크를 남기고 닫습니다 | 기획 |
| 마지막 PR 병합 | PR 본문의 `Closes #번호`로 Issue를 자동 종료합니다. 기획 검수 결과는 닫기 전에 코멘트로 남깁니다 | 개발 |

- Projects 보드, 마일스톤, 제품 분류 라벨은 쓰지 않습니다. 라벨로 GitHub Claude를 실행하지 않습니다. 열린 Issue 목록이 곧 작업판입니다.
- Issue 본문은 처음 합의한 목표의 기록이므로 고치지 않습니다. 변경은 코멘트로 쌓습니다. 체크박스에 표시하는 것은 내용 변경이 아니므로 괜찮습니다.

- [BGLike 서버](https://discord.com/channels/1554865028006547549/1554865028837015667)의 `#일반`에서 짧은 질문과 일정을 공유합니다. 게임 화면을 함께 볼 때는 음성 `플레이테스트` 채널을 사용합니다.
- `#github-알림`에는 PR 병합과 닫힘만 알립니다. [Discord PR 알림 워크플로우](../.github/workflows/discord-pr.yml)는 같은 저장소의 브랜치에서 만든 PR만 처리합니다.
- [Godot 워크플로우](../.github/workflows/godot.yml)의 `notify` 작업은 정책 또는 게임 검사 실패를 알립니다. 정상 실행 결과는 GitHub Actions에서 확인합니다. Discord 전송 실패가 검사 결과를 바꾸지 않습니다. 중복 알림을 막기 위해 기존 GitHub 저장소 웹훅은 삭제했습니다.
- 두 워크플로우는 GitHub Actions의 `DISCORD_PR_WEBHOOK_URL` 저장소 비밀값을 사용합니다. Discord 웹훅 URL을 문서나 채팅에 공유하지 않습니다.
- 채팅이나 통화에서 확정한 작업 범위와 결정은 해당 GitHub Issue 또는 PR에 기록합니다. 동료의 Discord 사용자명 확인 전에는 초대하지 않습니다.

## 브랜치와 병합

1. 최신 `main`에서 `feat/4-combat-prototype`처럼 짧은 브랜치를 만듭니다. 브랜치 이름, 커밋 메시지, PR 제목은 [브랜치와 커밋 규칙](GIT_CONVENTIONS.md)을 따릅니다.
2. 한 PR은 한 목표에 집중합니다. 가능하면 하루 안에 검토할 수 있는 크기로 나눕니다.
3. 작성자는 PR 양식에 관련 Issue, 변경 내용, 검증 결과를 기록합니다. 필요하면 상대방에게 검토를 요청합니다.
4. 필수 CI와 [독립 리뷰 절차](agents/review.md)를 확인하고 지적을 처리합니다. 맡긴 작업의 `two-way/narrow` 변경은 최종 head의 독립 리뷰·필수 CI·Issue 합격 기준을 충족하면 로컬 에이전트가 별도 병합 위임 없이 squash merge합니다. `one-way/broad` 변경과 새 `contents: write` Draft 권한은 사람이 최종 head를 승인한 뒤 병합합니다. 동료 승인은 필수가 아닙니다. 병합한 브랜치는 삭제합니다.
5. `main`이 깨지면 다음 기능보다 복구를 우선합니다. 문제가 있는 변경은 작은 수정 PR 또는 revert로 되돌립니다.

### PR 생성과 CI 대기

조기 공유가 필요 없는 작업은 로컬 검사와 독립 리뷰 근거를 모은 뒤 일반 PR로 생성합니다. 구현 중 방향 확인이나 조기 피드백이 필요하면 Draft를 씁니다. 생성 전에 [Godot workflow](../.github/workflows/godot.yml)의 실행 조건을 확인합니다. Draft에서 ready로 바꾸면 같은 head도 새 CI가 시작되어 이전 실행이 취소될 수 있습니다.

로컬 에이전트의 검사·CI 대기 명령은 `~/.agents/skills-docs/agent-workflow.md`를 따릅니다. 실행마다 watcher 하나를 유지하고 비동기 세션을 이어 읽어 진척을 확인합니다. 새 head나 ready 전환으로 실행이 바뀌면 이전 결과와 구분해 최종 대상 실행을 기다립니다.

watcher 오류나 로그와 API 상태의 불일치가 있으면 해당 실행의 상태·로그와 GitHub 공식 장애 상태를 추가로 대조합니다. 정상 대기 중 진척은 watcher에서 받습니다. watcher나 로그의 성공은 [병합 직전 head·base·필수 체크 확인](agents/review.md#병합-실행)을 대신하지 않습니다.

미완성 기능도 `main`에 안전하게 넣을 수 있습니다. 실제 진입점에서 기본값을 꺼 두고, PR에 노출 조건과 제거 시점을 적습니다. 아직 기능이 없으므로 공통 기능 플래그 시스템은 만들지 않습니다.

`two-way`는 되돌릴 수 있는 변경입니다. `one-way`는 되돌리기 어려운 변경입니다. `narrow/broad`는 영향받는 사용자·데이터·권한·외부 시스템의 범위입니다. diff 크기로 위험을 판단하지 않습니다. 권한 확대, 되돌리기 어려운 데이터 변경과 외부 대량 발송은 위험 변경입니다. PR의 Merge Danger에 되돌리는 방법과 남는 외부 상태를 적습니다.

Draft CD의 실행 승인은 [Draft Release 절차](DRAFT_RELEASE.md)를 따릅니다. 공개 배포, production 변경, 외부 대량 발송과 데이터 삭제는 이 셋업의 범위 밖입니다.

## 검증과 보고

모든 변경은 `git diff --check`와 `python3 -m unittest discover -s scripts -p 'test_*.py'`를 확인합니다. 워크플로 변경은 `actionlint`도 실행합니다.
게임 코드·장면·리소스·프로젝트 설정 변경은 Godot headless import, 메인 장면과 기존 전투 회귀 검사를 실행합니다. 명령은 [README](https://github.com/minjunkim-dev/BGLike/blob/main/README.md), 검사 선택과 알 수 없는 변경의 전체 검사 경로는 [CI 구성](CI.md)을 따릅니다.
플레이 변경은 편집기에서 변경한 입력과 화면 흐름을 직접 확인합니다. 에이전트의 화면 확인은 기본으로 [화면 밖 실행](CAPTURE_VERIFICATION.md#화면-밖-실행-기본)을 쓰고 사용자의 macOS 화면 포커스를 가져가지 않습니다. CI 성공으로 조작감이나 화면 가독성을 확인했다고 보고하지 않습니다.
직접 확인을 시작하기 전에 대상 SHA·로컬 변경, 필수 사례·대표 해상도와 합격 기준을 고정합니다. 필수 사례의 입력·화면 증거가 모이면 종료합니다. 같은 입력에서 통과한 증거는 재사용합니다. 새 요청은 추가 범위로 기록하고 기존 사례를 전부 반복하지 않습니다. 임시 스크립트의 사전 검사와 실패·중단·재개는 [직접 확인 실행 기록](CAPTURE_VERIFICATION.md#직접-확인-실행-기록)을 따릅니다.
문서·설정 변경은 해당 설정을 읽는 도구 또는 GitHub 흐름을 확인합니다. PR에는 실행한 검증과 미확인 범위를 구분합니다. 게임 동작 변경은 사람이 편집기에서 확인할 항목도 적습니다.
[Issue 양식](../.github/ISSUE_TEMPLATE/task.md)과 [PR 양식](../.github/pull_request_template.md)은 CLI로 작성할 때도 제목 구조를 유지합니다. Issue 없는 문서·설정 작업은 관련 Issue를 "없음"으로 적습니다. 다른 사람의 PR 브랜치에 커밋을 추가하면 PR 코멘트로 알립니다.
기획 문서의 규칙·수치와 다르게 구현하려면 먼저 Issue에 질문을 남깁니다. 엔진 업그레이드와 외부 애드온 도입은 별도 Issue에서 합의합니다.

## AI 에이전트

사람은 목표·합격 기준과 위험한 변경의 최종 병합을 승인합니다. 구현·독립 리뷰·수정과 낮은 위험의 병합은 로컬 에이전트가 맡습니다. 병합은 위 위험별 정책을 따릅니다. 실제로 연결된 자동 AI 리뷰만 이 저장소 범위에서 정리합니다. 로컬 독립 리뷰·필요한 보안 리뷰, 결정적인 보안 스캔, dependency 검사와 CI는 유지합니다. 다른 저장소의 App 접근과 계정 연결은 변경하지 않습니다.

**기본: 로컬 앱으로 구현**

1. 사람이 Issue에 목표와 완료 조건을 적습니다.
2. Claude Code나 Codex 데스크탑 앱에 Issue 번호를 주고 구현합니다. 결정적인 자동 검사를 실행합니다. 플레이 변경에는 편집기 확인 결과와 미확인 항목을 적습니다.
3. [독립 리뷰 절차](agents/review.md)에 따라 Standards와 Spec을 각각 별도 컨텍스트에서 검토합니다. 위험 변경에는 별도 Security 검토를 추가합니다. 같은 모델이면 같은 모델의 별도 컨텍스트라고 기록합니다.
4. 파일 소유권을 나눕니다. 수정 권한을 받은 리뷰어는 범위 안의 확실한 결함을 직접 수정하고 커밋합니다. 읽기 전용 Claude 리뷰는 [사전 승인 범위](#읽기-전용-claude-리뷰의-사전-승인)를 따릅니다. 읽기 전용 승인으로 쓰기 권한을 늘리지 않습니다.
5. 최종 head의 전체 diff를 다시 독립 검토합니다. 필수 CI와 합격 기준을 확인합니다. 병합은 위 위험별 정책을 따릅니다. 필요한 PR에만 Bugbot 수동 보조 리뷰를 요청합니다.

로컬에서는 작업 중에 방향을 바로잡고 편집기로 플레이해 볼 수 있습니다. GitHub의 추가 Claude 리뷰 workflow는 사용하지 않습니다.

**GitHub 범위의 자동 AI 리뷰 확인**

현재 저장소의 workflow, GitHub 리뷰 설정, GitHub App 접근, 최근 PR 봇 코멘트·check와 branch protection을 확인합니다. App 설치만으로 자동 리뷰가 켜졌다고 판단하지 않습니다. 과거 코멘트만으로 현재 연결을 판단하지 않습니다. 연결이 없음을 확인하면 해당 경로를 `비해당`으로 기록합니다. 권한 부족 등으로 확인하지 못하면 `미확인`으로 기록합니다. 서비스 목록에서 저장소를 찾지 못한 것은 비활성화 증거가 아닙니다.

ChatGPT·Codex Cloud 계정 설정과 서비스의 저장소 목록 탐색은 이 셋업 범위에서 제외합니다. OAuth를 재연결하지 않습니다. App 접근을 바꿔야 하면 이 저장소에 한정하고 다른 용도의 접근을 보존합니다. 확인 한계로 독립적인 문서·CI/CD·로컬 리뷰·수동 Bugbot 작업을 중단하지 않습니다.

- 외부 fork는 Secret이 없는 환경에서 사람이 검토합니다.

### 읽기 전용 Claude 리뷰의 사전 승인

2026-10-03 GitHub 계정 `minjunkim-dev`(MINJUN KIM)는 "보류하지말고 읽기 전용 리뷰로 보내", "리뷰가 필요하면 해야지"라고 지시했습니다 ([Issue #12의 승인 기록](https://github.com/minjunkim-dev/BGLike/issues/12#issuecomment-5967003737)). 이 절은 `minjunkim-dev`가 맡긴 BGLike 작업의 **로컬 Claude Code 독립 읽기 전용 리뷰**에 대한 승인 기록입니다. 다른 협업자의 승인을 대신하지 않습니다.

이 승인은 현재 요청자가 `minjunkim-dev` 본인임을 확인했을 때만 씁니다. 로컬 세션에서 `gh auth status`로 로그인 계정을 확인하는 식입니다. 다른 협업자가 요청했거나 요청자를 확인할 수 없으면 이 승인을 쓰지 않고 요청마다 승인을 받습니다. 다른 협업자도 사전 승인하려면 이 절에 계정과 승인 기록을 따로 추가합니다.

리뷰에 필요한 이 저장소의 코드와 기획·협업 문서를 **Anthropic Claude 서비스로 전송할 수 있습니다.** 비밀값(인증 토큰, 웹훅 URL)과 작업에 관계없는 개인 파일은 제외합니다. GitHub Claude 실행과 쓰기 가능한 에이전트 실행은 이 승인에 포함하지 않습니다.

- 리뷰어에게는 파일 읽기·검색과 분석만 허용합니다. 파일 수정, 커밋, push, 배포 권한은 포함하지 않습니다. 로컬 CLI에서는 `Read`, `Glob`, `Grep`만 허용합니다.
- 같은 서비스·목적·읽기 전용 범위의 리뷰는 승인 질문을 반복하지 않고 진행합니다. 실행 요청에 결정 날짜(2026-10-03), 서비스(Anthropic Claude), 목적(독립 읽기 전용 리뷰), 전송할 파일 경로, 허용 도구와 제외 대상을 명시합니다.
- 서비스, 목적 또는 권한 범위를 늘리려면 사용자 승인을 받습니다. 이 승인은 철회 전까지 위 범위에서 유효합니다. `minjunkim-dev`가 철회하면 즉시 적용을 중지하고 이 기록을 갱신합니다.
- 자동 승인이 거부되면 원래 사용자 지시와 자료·권한 범위를 확인해 승인 근거를 보완합니다. 그래도 차단되면 이유를 알리고 사용자에게 확인합니다. 이 문서는 실행 환경의 자동 승인 검사나 보안 정책을 끄거나 우회하는 설정이 아닙니다.
