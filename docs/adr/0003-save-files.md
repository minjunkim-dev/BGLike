# 0003. 자동 저장은 `user://save.bin` 한 슬롯의 버전 머리 + Variant 바이너리, 설정은 `user://settings.cfg`

- 상태: 채택 (2026-10-22)
- 구분: 개발 결정. 저장 파일의 위치·형식·버전 처리는 [#209 기획자 답](https://github.com/minjunkim-dev/BGLike/issues/209#issuecomment-6330756631)이 개발 결정으로 남겼다. 기획자가 나중에 바꿀 수 있다.
- 관련: [Issue #280](https://github.com/minjunkim-dev/BGLike/issues/280). 이 기반을 쓰는 Issue는 [#281](https://github.com/minjunkim-dev/BGLike/issues/281)(전투 상태), [#282](https://github.com/minjunkim-dev/BGLike/issues/282)(정비·보상 화면), [#284](https://github.com/minjunkim-dev/BGLike/issues/284)(새 게임·이어하기), [#285](https://github.com/minjunkim-dev/BGLike/issues/285)(설정)

## 맥락

기획 결정(#209 4·7·8·9번): 자동 저장 한 슬롯에 전투 상태 전체를 행동이 끝날 때마다 저장한다. 난수 상태도 저장한다. 정비·보상 화면 중에도 저장한다. 졸업 화면이 뜨면 저장을 지운다. 설정(마스터 음량, 창 모드)은 게임 저장과 따로 두고 새 게임·졸업이 지우지 않는다.

저장할 값에는 Godot `RandomNumberGenerator.state`(64비트 정수), `Vector2i` 칸 좌표와 그 좌표를 키로 쓰는 Dictionary가 들어간다. 행동마다 쓰므로 쓰는 도중 게임이 꺼질 수 있다.

## 결정

### 위치

| 파일 | 경로 | 지우는 때 |
| --- | --- | --- |
| 게임 저장 | `user://save.bin` | 새 게임, 졸업(`GameSave.delete()`) |
| 설정 | `user://settings.cfg` | 지우지 않음 |

`user://`는 Godot 기본값을 쓴다. macOS는 `~/Library/Application Support/Godot/app_userdata/BGLike/`, Linux는 `~/.local/share/godot/app_userdata/BGLike/`다. 편집기 실행과 내보낸 게임이 같은 폴더를 쓴다. 자동 검사는 `user://tests/save/<프로세스 ID>/`로 경로를 바꿔 개발자의 저장을 건드리지 않는다.

### 형식

게임 저장 파일은 8바이트 머리와 본문이다.

| 바이트 | 내용 |
| --- | --- |
| 0–3 | `BGLS`(ASCII) |
| 4–7 | 형식 버전(u32 little-endian). 지금 `1` |
| 8– | `var_to_bytes()`로 만든 본문 |

본문은 `{"act": int, "stage": int, "sections": Dictionary}`다.

- `act`·`stage`는 요약(`GameSave.summary_text()`: "3막 2스테이지 진행 중")에 쓴다. 이어하기 전에 본문 전체를 해석하는 쪽에 맡기지 않고 바로 보여 줄 수 있다.
- `sections`는 저장하는 쪽이 이름별로 채운다. 예를 들어 #281은 `"combat"`, #282는 `"preparation"`을 넣는다. 저장하는 쪽은 자기 칸을 만들고 읽을 수 있다. 칸을 더해도 파일 머리와 본문 틀은 그대로다.
- `bytes_to_var()`는 Object를 복원하지 않는다(`bytes_to_var_with_objects()`와 다르다). 저장 파일로 스크립트나 리소스를 불러올 수 없다. 그래서 `sections`에는 Object가 아닌 값(정수, 실수, 문자열, 벡터, 배열, Dictionary, Packed 배열)만 넣는다.

설정 파일은 Godot `ConfigFile` 텍스트(`[settings]` 섹션)다. 키는 #285가 정했다: `master_volume`(정수 %, 기본 80, 10% 단계)과 `fullscreen`(bool, 기본 `false`). `GameSettings.volume()`은 손으로 고친 값을 0–100의 한 단계 값으로 맞춘다. 화면과 단계의 근거는 [설정 화면](../COMBAT_UIUX.md#설정-화면)에 있다. `GameSettings.read(key, fallback)`는 파일이 없거나 깨졌거나 값의 타입이 `fallback`과 다르면 `fallback`을 돌려준다.

### 버전 처리

- 형식 버전이 `FORMAT_VERSION`과 다르면(높든 낮든) 읽지 않는다. 본문도 해석하지 않는다.
- 본문의 모양(어느 칸이 있고 어떤 타입인지)을 호환되지 않게 바꾸면 `FORMAT_VERSION`을 올린다. 새 `sections` 칸을 처음 추가하는 것은 바꿈이 아니다. 그 칸이 없는 옛 저장은 저장하는 쪽이 "읽을 수 없음"으로 처리한다.
- 출시 전에는 옛 버전을 변환하지 않는다. 출시 뒤 옛 저장을 살려야 하면 `read()`에 N-1 → N 변환 단계를 더한다.

### 읽을 수 없는 저장

다음은 모두 "저장을 읽을 수 없음"이다. `GameSave.read()`가 빈 Dictionary를 돌려주고 `push_warning`으로 이유를 남긴다. 게임은 멈추지 않는다.

- 8바이트 이하, 머리가 `BGLS`가 아님, 형식 버전이 다름
- 본문을 해석할 수 없음(잘림, 쓰레기 값)
- 본문이 Dictionary가 아니거나 `act`·`stage`가 정수가 아니거나 `sections`가 Dictionary가 아님

`has_save()`는 파일이 있는지만 본다. 파일은 있는데 읽을 수 없는 경우의 화면은 [#284](#새-게임이어하기졸업-284)가 정했다. `summary_text({})`는 "저장을 읽을 수 없음"을 돌려준다.

### 원자적 쓰기

`GameSave.write_atomic()`은 `<경로>.tmp`에 다 쓰고 닫은 뒤 `DirAccess.rename_absolute()`로 바꿔치기한다. 쓰기 오류가 있거나 닫은 임시 파일의 크기가 쓴 바이트 수와 다르면(디스크 부족) 바꿔치기하지 않는다. 쓰는 도중 종료되면 `.tmp`만 반쯤 남고 원래 파일은 이전 저장 그대로다. 다음 쓰기가 `.tmp`를 덮어쓴다. `delete()`는 `.tmp`도 지운다. 설정 파일도 같은 함수로 쓴다.

### 검사

`tests/save_test.gd`가 `make check`(`scripts/check_godot.sh`)에서 실행된다. 정상 왕복(64비트 난수 상태, `Vector2i` 키 포함), 버전 0·2, 깨진 파일 9가지, 반쯤 쓴 `.tmp`, 임시 파일을 열 수 없는 쓰기 실패, 저장 삭제 뒤 설정 유지, 깨진 설정 파일을 검사한다.

### 전투 칸 (#281)

[#281](https://github.com/minjunkim-dev/BGLike/issues/281)이 `sections["combat"]`을 채운다. 2026-10-22 개발 결정이다. 저장할 상태 목록과 어려운 부분은 [#281 착수 전 범위 확인](https://github.com/minjunkim-dev/BGLike/issues/281#issuecomment-6337219731)에 적었다.

- 내용: 스테이지 번호, 이번 드랍과 굴림 여부, 공용 가방, 유닛 목록(새끼 거미는 생성 순서대로 뒤에), 턴 순서와 묶음 진행, 상자·바위, 장판, 전투 주사위의 `RandomNumberGenerator.state`, 마지막 조작 아군. 유닛끼리의 참조(기절·표식·상태 이상·장판)는 유닛 목록의 번호로 적는다. 지형은 스테이지 데이터에서 다시 만든다.
- 시점: 행동이 끝나고 연출·반응 확인 창을 기다리지 않는 첫 프레임(`battle.gd`의 `_process`)과 적 행동 하나가 끝날 때마다(`_pause_enemy_action`).
- 적 턴 중간: 적 AI는 한 턴의 진행을 코루틴 지역 값으로 들고 있어 중간 상태에서 다시 시작하면 다른 선택을 할 수 있다. 그래서 적 턴 중의 저장은 그 적 턴이 시작한 상태와 `replay: {actions, reactions}`(끝낸 적 행동 수, 아군의 반응 답)다. 복원은 시작 상태로 되돌리고 다음 프레임에 끝낸 행동까지 연출·팝업·소리 없이 같은 난수로 다시 실행한다. 답한 반응은 다시 묻지 않는다.
- 드랍: 승리 순간의 드랍을 전투 주사위로 굴린다. 마지막 공격 전의 저장에서 이어해 같은 공격을 해도 같은 드랍이 나온다.
- 검사: `restore_combat()`은 스테이지와 유닛 구성, 유닛 번호, 지도 안의 칸, 변수 타입, 상태 이상·물체·장판 종류, 아이템(아이템 데이터의 한 종류이고 수치만 그 범위 안의 정수로 다른 것)을 모두 확인하고, 정수·목록 길이·다시 실행 수에 상한을 둔다(고친 저장이 끝나지 않는 적 턴을 만들지 않게). 턴 순서는 살아 있는 유닛 전부이고 현재 차례가 있어야 하며, 기절은 살아서 순서에 있는 시전자만 허용한다. 그리고, 맞지 않으면 전투를 바꾸지 않고 `false`를 돌려준다.
- 스위치: `GameSave.autosave`가 켜져 있을 때만 쓴다. 기본은 꺼짐이고 타이틀의 `새 게임`·`이어하기`가 켠다([#284](#새-게임이어하기졸업-284)). 이어하기는 장면을 연 직후 첫 프레임 전에 `restore_save(GameSave.read().get("sections"))`([정비 칸](#정비-칸-282))를 불러 1-1 시작 상태가 저장을 덮지 않는다.
- 검사: `tests/combat_save_test.gd`가 실제 연출을 켠 채(빠른 시간 배율) 9개 스테이지를 같은 규칙의 입력으로 진행해 저장한 모든 시점을 새 장면에 복원하고, 시점별로 이어서 같은 저장·상태가 나오는지 확인한다.

### 정비 칸 (#282)

[#282](https://github.com/minjunkim-dev/BGLike/issues/282)가 보상 확인·정비 화면이 열려 있는 동안 `sections["preparation"]`을 더한다. 2026-10-22 개발 결정이다. 새 칸이라 `FORMAT_VERSION`은 그대로다.

- 내용: `{"maintaining": bool}`(보상 확인 단계면 `false`, 정비 단계면 `true`) 하나다. 가방, 장비, 캐릭터별 물약, 남은 보상, 드랍 굴림 여부는 같은 저장의 `combat` 칸에 이미 있다. 고른 칸, 열린 폐기·정비 종료 확인 창, 정비 종료 확인 생략 선택(`더 이상 이 메시지를 띄우지 않음`)은 저장하지 않는다. 이어하기는 같은 화면 단계에서 아무것도 고르지 않은 채 시작하고 정비 종료 확인을 다시 묻는다.
- 시점: 화면을 열 때, 정비하기를 누를 때, 보상 수령, 장착·교체·해제, 물약 주기·넘기기, 폐기를 확정한 뒤의 첫 프레임에 전투 저장과 같은 `_autosave`로 쓴다. 같은 `GameSave.autosave` 스위치를 따른다. 정비를 마치면 받지 않은 보상을 가방에 넣고 다음 전투를 시작한다. 그 시작 상태가 `combat` 칸만 있는 저장으로 남는다.
- 이어하기: `battle.restore_save(sections)`가 정비 칸을 검사하고 `restore_combat(sections.combat)`을 부른 뒤 화면을 그 단계로 다시 연다. 정비 칸이 없으면 `restore_combat()`과 같다.
- 검사: 정비 칸은 키가 `maintaining` 하나이고 bool이어야 한다. 정비 화면은 드랍을 굴린 승리 뒤에만 열리므로 전투 칸이 맞고(`restore_combat()`과 같은 검사), `rewarded`가 참이고 살아 있는 적이 없어야 한다. 맞지 않으면 전투를 바꾸지 않고 `false`다.
- 검사: `tests/combat_preparation_save_test.gd`가 각 동작 뒤의 저장이 그 순간의 상태와 같고, 새 장면에 복원하면 같은 화면 단계·가방·장비·물약·남은 보상으로 돌아오며 다시 저장하지 않는지 확인한다. 칸 선택과 확인 창은 저장하지 않음, 스위치가 꺼지면 쓰지 않음, 고친 정비 칸을 거부함도 본다.

### 새 게임·이어하기·졸업 (#284)

[#284](https://github.com/minjunkim-dev/BGLike/issues/284)가 타이틀과 졸업 화면을 저장에 연결한다. 2026-10-22 개발 결정이다.

- `새 게임`: 파일이 있으면 덮어쓰기 확인 창에 `summary_text(read())`("3막 2스테이지 진행 중" 또는 "저장을 읽을 수 없음")를 보이고, 기본 선택은 `취소`다. 확인하면 `delete()` 뒤 `autosave`를 켜고 게임 장면을 연다. 새 장면이라 가방·장비·물약은 처음 상태다. 첫 프레임에 1-1 시작 상태를 저장한다.
- `이어하기`: `read()`가 빈 Dictionary가 아닐 때만 보인다. 누르면 게임 장면을 트리에 넣어 `_ready`를 마친 뒤, 첫 프레임 전에 `restore_save()`를 부른다. 성공하면 `autosave`를 켜고 그 장면을 현재 장면으로 바꾼다. 실패하면 `autosave`를 켜지 않은 채 장면을 바로 지우고 타이틀에 남는다. 복원 실패 때 1-1 상태가 저장을 덮지 않는다.
- 읽을 수 없는 저장: 머리·본문을 읽을 수 없으면 타이틀을 열 때 `이어하기`를 숨기고 메뉴 아래에 "저장을 읽을 수 없어 이어할 수 없습니다."를 보인다. 머리는 읽히지만 복원 검사에 걸리면 `이어하기`를 누를 때 거르고 같은 안내를 보인다. 타이틀을 다시 열면 `이어하기`가 다시 보인다(복원 검사에는 게임 장면이 필요해 타이틀에서 미리 하지 않는다). 저장을 지우는 일은 사용자가 `새 게임`을 확인할 때만 한다.
- 졸업: 3-3 정비를 마쳐 `3막 졸업` 화면이 뜨는 순간 `delete()`한다. 졸업 뒤에는 `_can_save()`가 거짓이라 다시 쓰지 않는다. 졸업 화면의 버튼은 `타이틀로` 하나이고 일시정지 메뉴를 열지 않는다. `autosave`가 꺼진 검사·장면 직접 실행은 지우지도 않는다.
- 검사: `tests/continue_test.gd`가 실제 타이틀에서 새 게임 → 아군 행동 → 타이틀을 새로 열어 이어하기, 일시정지 메뉴 `타이틀로` 뒤 이어하기, 보상 확인·정비 화면에서 이어하기, 덮어쓰기 확인(문구·기본 선택·`Esc`·취소·확인 뒤 처음 상태), 다른 형식 버전과 맞지 않는 전투 칸, 졸업 때의 삭제·버튼·`타이틀로`를 검사한다. ADR 0002의 여섯 창에서 확인 창과 안내가 화면 안에 들어가는지 본다.

## 한계와 후속

- Godot `FileAccess`는 `fsync`를 하지 않는다. 프로세스 종료·강제 종료에는 이전 저장이 남는다. 운영체제가 디스크에 쓰기 전에 전원이 꺼지면 새 파일이 비어 있을 수 있다. 그때도 읽을 수 없는 저장으로 처리되어 게임은 멈추지 않는다.
- 내보내기 대상은 지금 Linux다. Windows의 `rename_absolute` 덮어쓰기는 확인하지 않았다. Windows 내보내기를 더할 때 확인한다.
- 비트 하나가 바뀐 손상처럼 해석은 되는 본문은 거르지 않는다. 체크섬은 실제로 그런 손상을 겪으면 더한다.
- 설정 파일의 `ConfigFile` 텍스트 파서는 `Object(...)` 값을 만든다. `read()`는 타입이 다른 값을 버리지만 만들어지는 것 자체는 막지 않는다. 사용자 폴더의 파일을 고칠 수 있는 사람은 이미 사용자 권한을 가진 것으로 보고 신뢰 경계 밖으로 둔다.
- `sections` 안의 값은 이 모듈이 검사하지 않는다. 채우는 쪽(#281·#282)이 복원할 때 타입과 범위를 검사하고, 맞지 않으면 읽을 수 없는 저장으로 처리한다.
- `user://` 위치를 나중에 `application/config/use_custom_user_dir`로 바꾸면 기존 저장·설정을 옮겨야 한다.

## 대안

- JSON: 사람이 읽기 쉽지만 숫자가 64비트 실수라 난수 상태(64비트 정수)가 깨지고 `Vector2i`·키 타입을 직접 바꿔야 한다. 택하지 않았다.
- `var_to_str()`·`ConfigFile` 텍스트로 게임 저장: 타입은 보존하지만 텍스트 파서가 `Object(...)` 값을 만들 수 있다. 행동마다 쓰는 저장은 사람이 직접 고칠 일이 없다. 택하지 않았다. 설정은 값 몇 개뿐이고 타입이 다르면 기본값을 쓰므로 `ConfigFile`을 쓴다.
- 버전 없는 파일: 형식을 바꾼 뒤 옛 파일을 잘못 해석할 수 있다. 택하지 않았다.
- 저장하는 쪽을 등록하는 레지스트리: 저장 시점에 부르는 쪽(전투, 정비 화면)이 칸을 모두 알고 있어 필요 없다. 택하지 않았다.
- 여러 슬롯·직접 저장: 기획 결정(#209 7번) 범위 밖이다.
